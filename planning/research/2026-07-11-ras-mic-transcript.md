## Distilled ideas (for assessment)

1. **Structured ticket intake (Linear).** Feature requests and bug reports live in Linear with a rich schema: summary, steps to reproduce, expected behavior, actual behavior, impact analysis, suggested next steps. Tickets are often AI-authored. The ticket IS the loop's success criterion.
2. **MCP assignment to a cloud agent.** A Linear ticket is assigned to an agent (Cursor Cloud / Devin) via MCP; work starts without the human at a keyboard. Cloud execution chosen for full desktop access and to keep the local machine free.
3. **Loop 1 — build/verify loop with computer use.** Agent implements, then runs the actual app on a desktop via computer use, reproduces the bug first ("experience the bug"), tests the fix, and records a video. Exit condition: a recording of the desired state actually happening. Failures feed back into the build step.
4. **Video-as-evidence on the PR.** The PR body embeds demo videos of the success state, so human review starts from proof, not from code.
5. **Loop 2 — scored review loop.** Greptile reviews the PR and emits a confidence score out of 5. The /gp loop skill: wait for review → if score < 5/5, address comments, push, wait again → break only at 5/5. Merge is gated on the score.
6. **Human role shifts to policy author.** Human writes/curates tickets and reviews the video + function signatures — not the full diff. Human is involved at every step only while building the loop the first time.
7. **Loop economics.** A loop only pays if the evaluation is "clear and cut" — easy to state, easy to check (defined in the ticket, confirmed via computer use). Fuzzy success states burn tokens/subscriptions.
8. **Manual-first loop authoring.** Walk each step manually with the agent, then codify it as a skill (his: "testing Pluto PRs"). Multiple explicit stop points (bad/hallucinated recording; score < 5/5 blocks merge) make the loop robust.
